# /codetodocs.run — Generate Documentation

Generate documentation for every component in the repository.

## 1. Prerequisites

1. Check that `.codetodocs/config.yaml` exists. If missing, tell the user to run `/codetodocs.init` first and stop.
2. Read and parse `.codetodocs/config.yaml`. Extract: `output_dir`, `target_branch`, `components`, `documents`, `exclude_defaults`.

## 2. Mode Detection

- If **no files** exist under `{output_dir}/` → **full-scan mode** (Section 4).
- If documentation already exists → **incremental mode** (Section 9).

## 3. Component Resolution

**If `components` is defined in config:**
- Use the defined list.
- **Overlapping paths**: If a file matches multiple components, warn and assign it to the first match.
- **Uncategorized**: Source files not matching any component path are grouped into an implicit `"uncategorized"` component.

**If `components` is NOT defined:**
- Treat the entire repo as one component named after the repository root directory (e.g., `/path/to/my-project` → `my-project`).

## 4. Full-Scan Generation

For **each** component, perform the following steps:

### 4.1 Discover Source Files

Find all source files within the component's paths.

- Always respect `.gitignore`.
- If `.codetodocsignore` exists at repo root, apply its patterns as additive exclusions (gitignore-style syntax). Report any invalid patterns and continue with valid ones.

**Always exclude these file types** (regardless of ignore files):
- Binary files (images, fonts, compiled artifacts, `.exe`, `.dll`, `.so`, `.o`, `.pyc`, `.class`)
- Lock files (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Gemfile.lock`, `Cargo.lock`, `poetry.lock`, `composer.lock`)
- Minified/bundled files (`*.min.js`, `*.min.css`, `*.bundle.js`, `dist/`, `build/`, `out/`)
- Vendored dependencies (`vendor/`, `node_modules/`, `third_party/`)
- Generated code (files with `// Code generated` or `# Generated by` headers, `*.generated.*`, `*.g.cs`, `*.pb.go`)
- Data/fixture files (`*.csv`, `*.sql` dumps, large JSON data files > 50KB)
- Media and assets (`*.svg`, `*.png`, `*.jpg`, `*.ico`, `*.woff`, `*.ttf`)

### 4.2 Analyze Structure First

Before reading file contents, build a map of the component:

1. **List the full file tree** for the component's paths (names and directories only).
2. **Identify high-priority files** that should be read in full:
   - Entry points (`main.*`, `index.*`, `app.*`, `Program.cs`, `Startup.cs`, `__main__.py`)
   - Configuration files (`*.config.*`, `*.yaml`, `*.yml`, `*.toml`, `*.json` config files, `Dockerfile*`)
   - READMEs and existing documentation (`README*`, `RUNBOOK*`, `CHANGELOG*`)
   - Route/controller/handler definitions (API surface)
   - Dependency manifests (`package.json`, `*.csproj`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`)
3. **Identify standard-priority files** to read at signature level (public interfaces, class/function declarations, exported symbols — skip function bodies):
   - Service/business logic files
   - Model/entity definitions
   - Middleware and utility modules
4. **Identify low-priority files** to skip or sample (read only if needed for missing context):
   - Test files (`*_test.*`, `*.test.*`, `*.spec.*`, `test_*`, `tests/`)
   - Test fixtures and mocks
   - Build scripts and CI configuration
   - Migration files (read only the latest few)

### 4.3 Read Sources & Templates

Using the priority map from 4.2:

1. **Read high-priority files** in full.
2. **Read standard-priority files** at signature level — focus on exports, class declarations, function signatures, type definitions, and doc comments. Skip implementation bodies.
3. **Skip low-priority files** unless context gaps remain after steps 1-2.
4. **File size cap**: For any individual file over 500 lines, read the first 100 lines (imports, declarations) and the public API surface. Skip internal implementation details.
5. Load templates from `.codetodocs/templates/` — **skip any excluded by `exclude_defaults`**:
   - `technical_doc.md` (skip if `exclude_defaults` contains `technical`)
   - `product_doc.md` (skip if `exclude_defaults` contains `product`)
   - `ai_context.json` (skip if `exclude_defaults` contains `ai_context`)

### 4.4 Generate Documentation

Produce artifacts per component. Generate the three default types **unless excluded by `exclude_defaults`**. If `exclude_defaults` lists a type, skip it entirely — do not generate the file or create its output subdirectory.

Valid `exclude_defaults` values: `technical`, `product`, `ai_context`.

#### a. Technical Documentation → `{output_dir}/technical/{component}.md`

**Skip this artifact if `exclude_defaults` contains `technical`.**

Follow `.codetodocs/templates/technical_doc.md`. Include these sections:

| Section | Content |
|---|---|
| Purpose | What the component does and why it exists |
| Architecture | High-level design, key patterns, data flow |
| Setup / Installation | Prerequisites, install steps, environment |
| Running | How to run, dev mode, build commands |
| Configuration | Config files, env vars, defaults |
| Key APIs | Public interfaces, endpoints, signatures |
| Edge Cases | Known limitations, gotchas, error scenarios |
| Dependencies | Internal and external dependencies |

**Audience:** Engineers — be precise, include code-level details.

**Writing style:**
- Lead each section with 1-2 summary sentences, then use bullet points or tables for details.
- Use code blocks for commands, config examples, and API signatures — not prose.
- Omit obvious information (e.g., don't explain what `npm install` does).
- Keep the full document scannable in under 5 minutes. Aim for brevity over completeness — link to source files for deeper detail rather than reproducing code.

#### b. Product Documentation → `{output_dir}/product/{component}.md`

**Skip this artifact if `exclude_defaults` contains `product`.**

Follow `.codetodocs/templates/product_doc.md`. Include these sections:

| Section | Content |
|---|---|
| Purpose | Business value and problem solved |
| Features | User-facing capabilities |
| Business Rules | Policies, constraints, logic |
| User Impact | How changes affect end users |
| Configuration / Policies | User-configurable behaviors |

**Audience:** Product managers — focus on user value, avoid implementation details.

**Writing style:**
- Write in plain language. No jargon, no code, no internal class names.
- Use short paragraphs (2-3 sentences max) and bullet lists.
- Each feature entry should be one line: name + what it does for the user.
- Omit implementation details entirely — if a PM wouldn't care, leave it out.
- Keep the full document readable in under 3 minutes.

#### c. AI Context JSON → `{output_dir}/ai/{component}.json`

**Skip this artifact if `exclude_defaults` contains `ai_context`.**

Follow `.codetodocs/templates/ai_context.json`. Required top-level keys:

```
_codetodocs   → { component, generated (ISO 8601), schema_version: "1.0" }
component     → { name, description }
modules       → [ { path, purpose, exports } ]
api           → { functions: [{ name, signature, description }],
                  classes: [{ name, signature, description, methods }] }
types         → [ { name, definition } ]
configuration → { files, env_vars }
dependencies  → { internal: [], external: [] }
metrics       → { files_analyzed, modules_documented }
```

**Audience:** AI agents — structured for RAG retrieval. Must be valid JSON.

**Scope rules — keep the AI context concise and useful:**

- **Modules**: Group files into logical modules/namespaces (e.g., `src/services/`, `src/models/`). List one entry per module directory, NOT one entry per file. Use the `purpose` field to summarize what the module does and `exports` to list its key public symbols.
- **API surface only**: Document only **public/exported** functions, classes, and methods. Skip private/internal helpers, test utilities, and implementation details. A function is "public" if it is exported, part of an interface/contract, or called from outside its module.
- **Classes**: Include only public methods. Skip private methods, constructors with no notable logic, and boilerplate (getters/setters, `toString`, etc.).
- **Types**: Include only types that appear in public API signatures or are important domain models. Skip internal DTOs, helper types, and framework-generated types.
- **Configuration**: List only user-facing config variables and environment variables. Skip build-time or CI-only configuration.
- **Size target**: Aim for the AI context JSON to be **under 200 lines** for a typical component. If a component has an unusually large public API, prioritize the most important interfaces and note "Additional APIs documented in technical docs" in the description.
- **No file-per-file listing**: The `modules` array should contain **5-20 entries** representing logical groupings, not hundreds of individual file entries.

### 4.5 Header Markers

Before writing any docs, obtain the current UTC timestamp by running:
```bash
date -u +"%Y-%m-%dT%H:%M:%SZ"
```
Use this **exact value** (with full date AND time, e.g., `2026-02-09T17:42:03Z`) for all generated files in this run. Do NOT use midnight (`00:00:00Z`) or a date-only value.

- **Markdown docs**: Prepend the following as the first line:
  ```
  <!-- CodeToDocs | Component: {component-name} | Generated: 2026-02-09T17:42:03Z -->
  ```
- **JSON docs**: Set `_codetodocs.generated` to the same full timestamp string (e.g., `"2026-02-09T17:42:03Z"`).

### 4.6 Write Files

Write all generated files to the output directory. Create subdirectories (`technical/`, `product/`, `ai/`) as needed.

## 5. Custom Documents

If `documents` is defined in config, for each entry:

1. Read the template from the entry's `template` path.
2. Generate content targeting the specified `audience`.
3. Write to the entry's `output` path, replacing `{component}` with the component name.
4. If the template file is missing, report the error and skip that document.

## 6. Self-Correction Validation

After generating **each** document:

- **Markdown**: Verify the header marker comment is present.
- **JSON**: Verify output is valid JSON and contains the `_codetodocs` metadata object.
- On failure: attempt to regenerate **once**. If still invalid, report the error and continue.

## 7. Update AI Agent Instructions

**Skip this entire section if `exclude_defaults` contains `ai_context`** (no AI context files were generated).

After all AI context JSON files have been generated, update the repository's AI agent instructions file to reference the generated documentation.

### 7.1 Detect Instructions File

Check for these files in order of priority:
1. `AGENTS.md` (repo root)
2. `.github/copilot-instructions.md`

If neither exists, create `AGENTS.md` at the repo root.

### 7.2 Check for Existing Reference

Search the detected file for an existing CodeToDocs section (look for `<!-- codetodocs:start -->` marker). If found, replace the content between `<!-- codetodocs:start -->` and `<!-- codetodocs:end -->` markers. If not found, append the section to the end of the file.

### 7.3 Write Reference Block

Insert or update the following block, listing all generated AI context files:

```markdown
<!-- codetodocs:start -->
## AI Documentation

This repository has auto-generated AI context documentation. These files provide structured information about the codebase for AI coding agents and RAG retrieval:

{for each component:}
- `{output_dir}/ai/{component}.json` — Structured context for {component}: modules, APIs, types, configuration, and dependencies.
{end for}

These files are generated by [CodeToDocs](https://github.com/codetodocs/codetodocs). To regenerate, run `/codetodocs.run`.
<!-- codetodocs:end -->
```

### 7.4 Preserve Existing Content

- Do **not** modify any content outside the `<!-- codetodocs:start -->` / `<!-- codetodocs:end -->` markers.
- If the file has other sections, leave them untouched.

## 8. Error Handling

- **Component-level isolation**: If generation fails for one component, report the error and continue with remaining components.
- **Missing config**: Report error, suggest running `/codetodocs.init`.
- **Invalid target branch**: Report error, suggest verifying `target_branch` in config.

## 9. Summary Report

After all components are processed, print a summary:

## 10. Incremental Mode

When existing documentation is detected in `{output_dir}/`, use Git diff to update only affected components.

### 10.1 Identify Changed Files

Run the following to list files changed since the target branch:

```bash
git diff {target_branch}...HEAD --name-only
```

- If the target branch does not exist, report an error and suggest verifying `target_branch` in config.
- If there are no commits or no diff is possible, fall back to full-scan mode.

### 10.2 Map Changes to Components

For each changed file, determine which component it belongs to:

- Match the file path against each component's `paths` entries.
- If `components` is not defined, all changes map to the single implicit component.
- Collect the set of **affected components** (those with at least one changed file).

### 10.3 Classify Changes

**Not all** changes warrant a documentation update. The goal is to update docs only when the **public behavior, API surface, architecture, or configuration** of a component has meaningfully changed. Minor internal changes should be ignored.

For each affected component, classify the diff:

**Skip the component (no doc update needed) if changes are limited to:**
- Non-source files only (`.md`, `.txt`, `.gitignore`, lock files, CI config)
- Test files only (test additions, test fixes, test refactors)
- Internal refactors that don't change the public API or behavior (renaming private variables, reformatting, moving code within the same module)
- Bug fixes that don't change documented behavior or API contracts
- Dependency version bumps with no API changes
- Comments, whitespace, or formatting changes
- Log message changes
- Minor copy/string changes in non-user-facing code

Report these as "skipped (no doc-relevant changes)".

**Update docs only if changes include any of:**
- New or removed public APIs, endpoints, classes, or functions
- Changed function signatures, return types, or parameter types
- New or changed configuration options or environment variables
- Architectural changes (new modules, changed data flow, new dependencies)
- Changed business rules or validation logic
- New user-facing features or removed capabilities
- Breaking changes of any kind
- Significant changes to setup, build, or deployment steps

**Deleted files**: If files were deleted within the component but the component directory still exists, only update docs if the deleted files contained public APIs or features.

**Deleted component directory**: If the entire component directory has been deleted, prepend `<!-- ORPHANED: Component directory deleted -->` to the existing documentation files and report it.

### 10.4 Regenerate Affected Components

For each non-trivial affected component:

1. **Read full source files** for the component (for complete context).
2. **Read the Git diff** for focus: `git diff {target_branch}...HEAD -- {component-paths}`.
3. **Read existing documentation** for the component (to preserve structure and update in place).
4. **Read templates** from `.codetodocs/templates/`.
5. **Regenerate** only the non-excluded artifacts (technical, product, AI context) for the component, incorporating the changes. Respect `exclude_defaults` — do not regenerate excluded artifact types.
6. **Write** updated files with a new timestamp in the header marker.

Unchanged components' documentation files are **not modified** — their timestamps remain the same.

### 10.5 Incremental Summary

```
## CodeToDocs Run Summary (Incremental)

- **Changed files detected**: {count}
- **Affected components**: {count}
- **Regenerated**: {list}
- **Skipped (no changes)**: {list}
- **Skipped (no doc-relevant changes)**: {list}
- **Orphaned**: {list}
- **Errors**: {count}

### Files Updated
- {list each file path}
```
